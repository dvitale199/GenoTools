# GenoTools Testing & Regression Guide

This guide explains how testing works on the `refactor/main` branch — especially
the **old-vs-new parity** testing that gates the refactor before it merges to
`main`. It's written for a developer picking this up to run regression testing on
real cohorts.

If you only read one thing: the refactor's contract is **identical scientific
results to the pre-refactor code**. "Regression testing" here means proving that,
first on synthetic data (automated), then on real cohorts (your job — see
[Running parity on real data](#running-parity-on-real-data)).

---

## 1. Environment setup

Use the repo `.venv` (Python 3.11) for the **new** code:

```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install -e .
pip install pytest
```

PLINK/PLINK2 are downloaded automatically the first time a step needs them
(into `~/.genotools/misc/executables/`). You don't install them manually.

---

## 2. Running the test suite

```bash
.venv/bin/python -m pytest tests/unit tests/regression -q
```

- **`tests/unit/`** — fast, hermetic unit tests of the new modular code
  (`core/`, `qc/`, `gwas/`, `ancestry/`, `cli/`). No external baseline needed.
- **`tests/regression/`** — heavier tests that shell out to real PLINK and, for
  parity, to the pre-refactor CLI. Tests that need something absent (PLINK, the
  `.venv-stable` baseline, golden files) **skip cleanly** rather than fail.

Everything green today: **397 passed** with `.venv-stable` present.

## 3. Two kinds of regression testing

### 3a. Golden regression (self-consistency of the new code)

`tests/regression/test_qc_steps.py` compares the new code's output to committed
**golden files** under `tests/regression/golden/`. These were generated by the
new code, so they only prove the new code stays self-consistent (a step still
prunes the same samples/variants it did when the golden was captured).

Regenerate golden files if you *intentionally* change QC behavior:

```bash
.venv/bin/python tests/scripts/generate_golden.py \
    --geno tests/data/synthetic/genotools_test \
    --out tests/regression/golden
```

### 3b. Old-vs-new parity (the real regression gate)

`tests/regression/test_parity.py` runs the **pre-refactor CLI** and the **new
CLI** on the same input and asserts they agree. This is what proves the refactor
didn't change results. It needs a `.venv-stable` containing the old code.

**Build the baseline once:**

```bash
PYTHON=python3.11 bash tests/scripts/setup_stable_venv.sh origin/main
```

This creates `.venv-stable/` with the pre-refactor `genotools` installed from
`origin/main` (the last pre-refactor commit). Python 3.11 is required — the old
`umap-learn==0.5.3` doesn't build on 3.12+. On Linux the script also pre-caches
KING (see [KING on Linux](#king-on-linux)).

**Run parity on synthetic data:**

```bash
.venv/bin/python -m pytest tests/regression/test_parity.py -v
```

What it covers (all on `tests/data/synthetic/`):

| Test | Steps | Assertion |
|------|-------|-----------|
| `test_old_vs_new_qc_parity` | callrate, sex, het, geno, hwe | identical IDs **and** genotype content |
| `test_old_vs_new_multiword_qc_parity` | case_control / haplotype / ld | identical IDs **and** genotype content |
| `test_old_vs_new_full_pipeline_parity` | all_sample + all_variant | identical IDs **and** genotype content |
| `test_old_vs_new_gwas_parity` | pca + gwas | same tested-variant set + lambda within tolerance (see [decision B](#decision-b-gwaspca-region-exclusion)) |
| `test_old_vs_new_pca_ncount_parity` | pca 20 | both CLIs write a 20-PC eigenvec (non-default PC count reaches PLINK2) |
| `test_old_vs_new_gwas_external_covars_parity` | pca + gwas + covars | external covariates used identically; per-variant p-values agree (decision B N/A — PCA eigenvectors discarded for external covars) |

Note the old CLI uses **underscore** flags (`--case_control`, `--full_output`,
`--all_sample`) while the new CLI uses **hyphen** flags (`--case-control`,
`--full-output`, `--all-sample`); the test carries a per-step flag map so both
command lines build correctly.

## 4. What the comparators actually check (`tests/regression/compare.py`)

- **`compare_pfiles`** — sample and variant **ID sets** only.
- **`compare_genotypes`** — exports both pfile sets to PLINK2 `.traw` and
  compares the genotype matrix order-independently. Catches same-IDs-but-changed-
  genotypes and flipped allele coding, which `compare_pfiles` alone would miss.
- **`compare_gwas_results` / `compare_gwas`** — align two `--glm` association
  tables on variant ID, compare per-variant p-values and the derived genomic-
  inflation **lambda**. `find_gwas_output` locates the `.glm.*` file for a run.

So QC parity is checked on real genotype content, not just which IDs survived.

## 5. Running parity on real data

This is the main handoff task. Use the runner, which does the same thing as the
pytest parity suite but points at your cohort:

```bash
.venv/bin/python tests/scripts/run_parity.py \
    --geno /path/to/real_cohort \        # pfile prefix, no extension
    --out  /path/to/parity_workdir \
    --scenarios all                      # or: qc full-pipeline gwas
```

- `--geno` is a pfile prefix (`.pgen`/`.pvar`/`.psam`). The cohort is **copied
  into `--out` before running**, so your source data dir is never written to.
- It runs old (`.venv-stable`) and new (`python -m genotools`) for each scenario,
  compares, prints a PASS/FAIL summary, and exits non-zero if anything diverges.
- Scenarios: `qc`, `case_control`, `haplotype`, `ld`, `full-pipeline`, `gwas`
  (default: `qc full-pipeline gwas`).

Example output:

```
  [PASS] qc: identical IDs + genotypes
  [PASS] full-pipeline: identical IDs + genotypes
  [PASS] gwas: same tested-variant set; lambda old=1.00740 new=1.00712; per-variant p-mismatches=40498 (expected under decision B ...)
```

For ancestry parity you need a real reference panel + labels (not in the
synthetic data); run `genotools --ancestry --ref-panel ... --ref-labels ...`
under both CLIs and compare the predicted-label assignments. The default
`genotools` entry point still uses the **legacy** ancestry code, so ancestry
parity there is near-trivial; `genotools-new` (new `AncestryModel`) is
experimental and out of scope for this gate.

## 6. Decision B: GWAS/PCA region exclusion

GWAS parity is **not** asserted per-variant, on purpose. The new PCA pruning uses
PLINK2 `--exclude range` and correctly drops high-LD/MHC regions; the old code
used `--exclude` on a ranges file, which PLINK2 treats as a variant-ID list —
a **no-op** that excluded none of those regions. So the PCA eigenvectors (GWAS
covariates) differ slightly, and every GWAS p-value shifts a little. The
genomic-inflation **lambda still agrees** and the **tested-variant set is
identical**.

This was ratified as an intentional correctness fix ("decision B" in
`REFACTOR_HARDENING.md`): excluding those regions before PCA is standard practice.
So on **real data, expect GWAS per-variant p-values to differ slightly from the
pre-refactor baseline** — that is correct, not a regression. Parity is asserted
at the tested-variant-set + lambda level. A guard test
(`tests/unit/test_gwas/test_steps_regression.py::TestPcaExcludesHighLdRegions`)
locks the exclusion in so it can't silently revert to the old no-op.

QC and full-pipeline parity **are** exact (IDs + genotype content).

## 7. KING on Linux

The **pre-refactor** code calls `check_king()` at *module import* (top-level in
the old `qc.py`). On **Linux**, merely starting the old CLI therefore tries to
download KING from `kingrelatedness.com` — a slow, flaky host — even for QC/GWAS
runs that never use KING. (On macOS `check_king()` returns `None`, so this never
happens.) An un-cached download once hung CI for 17 minutes of retries.

`setup_stable_venv.sh` now pre-caches KING on Linux so the old CLI finds it and
skips the download. If that host is unreachable when you build `.venv-stable`,
the script warns you; you can drop any executable named `king` at
`~/.genotools/misc/executables/king` (parity steps never actually invoke it).
The new code uses lazy KING init and is unaffected.

## 8. Continuous integration (`.github/workflows/ci.yml`)

Runs on pushes to `main`/`refactor/main`, on every PR, and on manual dispatch.
Two parallel jobs on Ubuntu / Python 3.11:

1. **Unit + regression tests** — installs the new code, downloads PLINK/PLINK2,
   runs `pytest tests/unit tests/regression`. The parity tests skip here (no
   `.venv-stable`).
2. **Old-vs-new parity** — builds `.venv-stable` from `origin/main` and runs
   `tests/regression/test_parity.py`.

`~/.genotools` (the downloaded PLINK/PLINK2/KING) is cached between runs, so the
external download hosts are hit at most once per cache key.

## 9. Gotchas / FAQ

- **`.venv-stable` won't build on Python 3.12+** — use 3.11
  (`PYTHON=python3.11 bash tests/scripts/setup_stable_venv.sh`).
- **Parity tests all skip** — you haven't built `.venv-stable`, or PLINK2 isn't
  available. That's the intended fallback, not a failure.
- **Old CLI hangs on Linux** — KING download; see [KING on Linux](#king-on-linux).
- **A stray `<cohort>.pheno` appears** — GWAS writes `{input}.pheno` next to the
  input (pre-existing behavior, kept for parity). Both the runner and the GWAS
  tests copy the input to a temp/work dir first to avoid polluting source data;
  do the same in any ad-hoc runs.
- **`--warn` vs `--no-warn`** — the new CLI continues past a failed step by
  default (`--warn` behavior); pass `--no-warn` to fail fast. The old CLI's
  equivalent is `--warn True`/absent.
- **Where are the run logs?** — `{out}_all_logs.log` is the consolidated,
  step-tagged log; `{out}.json` has the structured metrics.
